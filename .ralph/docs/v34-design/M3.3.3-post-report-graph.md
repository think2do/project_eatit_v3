### 1.1 Parallel-not-sequential — 关键决策

post_report_graph 是**并行 fan-out**(START → coach_node ‖ reflection_node → END),与 turn_graph 不同:turn_graph 有 fan-in 节点 `next_question` 同步,本图**没有 fan-in 节点** — 两条分支各自直达 END。

理由(逐字翻译 Python `post_report_graph.py` line 9-15):

> The two nodes are independent — Coach is keyed on user, Reflection is keyed on session — so LangGraph schedules them concurrently. Each node delegates to a domain service that owns retries, persistence, and idempotency; failures inside one never starve the other.

Coach 输入 = `(user_id, recent_reports[])`,本质上是 **跨 session** 聚合;Reflection 输入 = `(session_id, report_payload, turns)`,本质上是 **单 session** 复盘。两者读取不同的输入维度,**互不依赖**。并行 fan-out 把端到端等待时间从 `T_coach + T_reflection`(顺序,可能 30-60s)降到 `max(T_coach, T_reflection)`(可能 15-30s),对 M3.4 UI "报告就绪后异步加载教练卡片 / 复盘 tab" 体验关键。

dev.d 在 `postReportGraph.ts` 注释里**逐字保留**这段 rationale,以阻止后续 reviewer 误把 post_report_graph 改回 sequential 形态(那会让用户在两个独立的 LLM 调用上串行等待)。

### 1.2 Fire-and-forget 模式 — graph 调用方契约

Spec line 1888 强调 **"Coach/Reflection 的 fire-and-forget 用 Promise(...).catch(noop) 实现,不阻塞主流程"**。

关键澄清:fire-and-forget 发生在 **graph 调用方(M3.4 UI 层)**,不在 graph 内部。

- **Graph 内部**:`coachNode` 与 `reflectionNode` 都被 `await`(LangGraph.js Pregel runtime 一定 await),graph 整体在两条分支都到 END 后才 resolve。这是 graph 的契约。
- **Graph 调用方(未来 M3.4)**:在用户看到"报告就绪"信号后,调用 `buildPostReportGraph(deps).invoke(state)` 但 **不 await**,而是 attach 一个 `.catch(noop)`。这样:
  - 报告 UI 立即可见(不等 30s)
  - Coach 卡片 + Reflection tab 在后台"懒加载",好后再 push 给 UI
  - LLM 错误被 swallow(noop catch),由 graph 内部的 try/catch 已经记录 error 字段;调用方不再处理
- **Python 对照**:Python `apps/api/app/domain/reports/service.py` line 55-85 `_spawn_post_report_coach_trigger` 用 `asyncio.create_task(graph.ainvoke(...))` + `add_done_callback(_POST_REPORT_TASKS.discard)`;TS 等价物用 `void graph.invoke(...).catch(noop)` 即可(JS 引擎不会 GC 掉一个被 catch chain 的 Promise,而 Python `asyncio.Task` 会被 GC 故需要保活集合;**TS 不需要保活集合**)。

本 doc 只锁 graph 自身契约。M3.4 UI 调用方代码不在本 loop 范围。dev.d 在 `postReportGraph.ts` 顶部注释中保留 fire-and-forget 契约说明,以便 M3.4 reviewer 不误把 invoke 改成 await。

**Judgment call A**:`pass_likelihood` 在 schema 层用 `z.string()` 还是 `PassLikelihoodSchema`?
- **方案选 `z.string()` (lenient)**。理由:LLM 经常输出 free-form("应该会过" / "不确定" / "中等" 等),如果在 schema 层用 `PassLikelihoodSchema`,Instructor 重试 3 次都失败 → ZodError 抛出 → 整个 Report 失败,UI 看不到任何报告。Python `coerce_pass_likelihood`(`apps/api/app/domain/reports/service.py` line 114-136)在 service 层强制 coerce → 这是 v3.1 验证过的模式。dev.a 的 `coercePassLikelihood` helper 在 sanitizers.ts 中实现,在 `runReportAgent` 返回前调用,把 raw string 强制映射到 3 档之一(§7.2)。
- 不用 `PassLikelihoodSchema`(strict)的代价:schema 不再保证返回类型一定是 3 档之一。**用 service 层 coerce 弥补**,且 `ReportAgentOutputSchema.pass_likelihood` 仍 `nullable().optional()` — 永不被持久化为非法值。

**Judgment call B**:`dimensions` 在 schema 层是否锁数量 5?
- **方案选 `default([])`(不锁)**。理由:LLM 偶尔只输出 3 dimension,strict 数量锁会导致 Instructor 重试失败 → 整个 Report 失败。`normalizeDimensions(dims)` helper 在 service 层补齐到 5 项,与 Python `apps/api/app/domain/reports/service.py` line 151-182 一致。
- DimensionScoreSchema **本身**仍锁 `name: DimensionNameSchema`(L0-1)— LLM 输出含非法 name(如 "组织架构")→ 该 dimension 直接 schema reject(单项不进 array),`normalizeDimensions` 把缺失的 5 项补 placeholder。

| 选项 | 优点 | 缺点 |
|------|------|------|
| **A. State 扩展**:PostReportState 增加 `coach_input` / `reflection_input` 字段,UI 调用方在 invoke 前填好 | 简单;state 自包含;dev.d 不需要 inject loader closures;mock 测试只需构造 plain object | state 字段从 5 个增加到 7 个;调用方多两个责任 |
| **B. Deps loaders**:`PostReportGraphDeps` 增加 `loadCoachInput(user_id, session_id): Promise<...>` / `loadReflectionInput(session_id): Promise<...>` closures | 隐藏数据加载;调用方只需 `(user_id, session_id)` | deps 里塞 closures 增加 mock 复杂度;不符合 Python "PostReportState fields set before ainvoke" 模式 |

**决策:方案 A(state 扩展)**。理由:
1. Python `PostReportState` 模型本身就含 `user_id` / `last_session_id`(在 invoke 前 caller 填),只是 Python service 内部再去 ORM 查 — TS 把这个 ORM 查询责任**前移到 caller**(M3.4 UI 层),保持 graph 内部逻辑纯。
2. Mock 测试更简单:contract test / parallel test 直接 `invoke({ user_id, last_session_id, coach_input: <fixture>, reflection_input: <fixture> })`,无需 mock 异步 loader。
3. M3.4 UI 调用方代码本身就要做 SQLite 查询(报告数据已在 Swift 侧持久化),在 caller 层 build input 与 dispatch graph 是合理职责划分。

代价:dev.d 需要在 §5 spec 短路逻辑 — 当 `coach_input === null` / `reflection_input === null`,对应 node 直接返回 `{coach_skipped: true}` 或 `{reflection_error: null}`(因 input 缺失时**不算错误**,而是 caller 决定 skip)。

## 4. Channel reducers

LangGraph.js 0.2.74 `channels` API:每字段 `{ reducer: (left, right) => merged, default: () => initial }`(同 turn_graph / intake_graph 模式)。

| Field | Reducer | Default | Notes |
|-------|---------|---------|-------|
| `user_id` | `(l, r) => r ?? l` | `() => ""` | input-only |
| `last_session_id` | `(l, r) => r ?? l` | `() => ""` | input-only |
| `coach_input` | `(l, r) => r ?? l` | `() => null` | input-only;TS port addition(§3.5) |
| `reflection_input` | `(l, r) => r ?? l` | `() => null` | input-only;TS port addition(§3.5) |
| `coach_skipped` | `(l, r) => r ?? l` | `() => false` | coach_node 写;**boolean `??` 注意**:`r=false ?? l = false`(只有 null/undefined 触发 fallback) |
| `coach_error` | `(l, r) => r ?? l` | `() => null` | coach_node 写;error 类名 string 或 null |
| `reflection_error` | `(l, r) => r ?? l` | `() => null` | reflection_node 写 |

**安全性论证**:两节点是**并行**写,但写不同 channel keys —
- `coach_node` 只写 `coach_skipped` + `coach_error`
- `reflection_node` 只写 `reflection_error`

不存在并行写同字段冲突(super-step merge 时各 channel 独立)。`(l, r) => r ?? l` 在两 node 各自 partial update merge 时绝不丢分支。

```ts
const channels: StateGraphArgs<PostReportState>["channels"] = {
  user_id:           { reducer: (l, r) => r ?? l, default: () => "" },
  last_session_id:   { reducer: (l, r) => r ?? l, default: () => "" },
  coach_input:       { reducer: (l, r) => r ?? l, default: () => null },
  reflection_input:  { reducer: (l, r) => r ?? l, default: () => null },
  coach_skipped:     { reducer: (l, r) => r ?? l, default: () => false },
  coach_error:       { reducer: (l, r) => r ?? l, default: () => null },
  reflection_error:  { reducer: (l, r) => r ?? l, default: () => null },
};
```

### 4.1 channel keys vs node names — 显式不冲突(§2.6 已 cross-check)

7 个 channel keys 与 2 个 node names 全无交集。dev.d 直接用字段名,无需 `_out` 后缀。

## 5. 二节点 Function 签名 + error isolation

```ts
export interface PostReportGraphDeps {
  llm: LLMProvider;  // M3.1.2 ArkProvider singleton
  logger?: {
    info?(msg: string, meta?: Record<string, unknown>): void;
    warn?(msg: string, meta?: Record<string, unknown>): void;
```

`deps` 通过 closure 注入(`buildPostReportGraph(deps)` 工厂模式,与 Python `build_post_report_graph(coach_service, reflection_service, gateway)` 对齐)。

### 5.1 coachNode — try/catch 严格 swallow

```ts
async function coachNode(
  state: PostReportState,
  deps: PostReportGraphDeps,
): Promise<Partial<PostReportState>> {
  // Caller didn't supply input ⇒ skip (not an error)
  if (state.coach_input === null) {
    deps.logger?.info?.("post_report_coach_node_skipped", { reason: "no_input" });
    return { coach_skipped: true, coach_error: null };
  }

  try {
    // dev.b owns runCoachAgent. coachNode wraps in try/catch; never throws.
    await runCoachAgent(state.coach_input, { llm: deps.llm });
    return { coach_skipped: false, coach_error: null };
  } catch (err) {
    const errorName = (err as Error)?.constructor?.name ?? "Error";
    deps.logger?.warn?.("post_report_coach_node_unhandled", { reason: errorName });
    return { coach_skipped: false, coach_error: errorName };
  }
}
```

**Critical contract**:`try/catch` MUST swallow ALL exceptions — 永不 throw 出 node。失败仅写 `coach_error` channel;并行的 `reflection_node` 不受影响。这是 §1.1 / §11.4 的核心。

**Logging key 锁**(L0 #11 审计):
- `post_report_coach_node_skipped` + `{reason: "no_input"}`(input 缺失 soft-skip)
- `post_report_coach_node_unhandled` + `{reason: errorClassName}`(LLM error / ZodError / network error 等)

dev.d 必须使用以上**精确字符串**(对齐 Python `post_report_graph.py` line 79)。

**Python 简化决策**:
- Python 用 `coach_service.maybe_trigger_after_report(user_id, last_session_id, gateway)` 内部检查 idempotency(`last_session_id` 是否与最近一次成功的 user_insight_cache 行相等),并管理 retry / persistence。
- **TS port 跳过 service 层**(spec 已声明,见任务上下文 "TS port simplification: skip the service layer; nodes call runCoachAgent / runReflectionAgent directly")。`coachNode` 直接调 `runCoachAgent`。Idempotency 由调用方(M3.4 UI 层)负责 — 同一 session 不重复触发 graph invoke。
- **Trade-off**:若调用方误重复 invoke,TS 会重复跑 LLM 调用 → 重复 Coach Insight 写入 SQLite(后续 M3.4 持久化时)。Mitigation:M3.4 UI 层使用 `last_session_id` 状态机 dedupe(本 doc §13.2 risk #3 备案)。

### 5.2 reflectionNode — try/catch 严格 swallow

```ts
async function reflectionNode(
  state: PostReportState,
  deps: PostReportGraphDeps,
): Promise<Partial<PostReportState>> {
  // Caller didn't supply input ⇒ skip; reflection_error stays null (not a true error)
  if (state.reflection_input === null) {
    deps.logger?.info?.("post_report_reflection_node_skipped", { reason: "no_input" });
    return { reflection_error: null };
  }

  try {
    await runReflectionAgent(state.reflection_input, { llm: deps.llm });
    return { reflection_error: null };
  } catch (err) {
    const errorName = (err as Error)?.constructor?.name ?? "Error";
    deps.logger?.warn?.("post_report_reflection_node_unhandled", { reason: errorName });
    return { reflection_error: errorName };
  }
}
```

**Same try/catch discipline**(symmetry critical for parallel safety):reflectionNode failure 不影响 coachNode。

**Logging key 锁**:
- `post_report_reflection_node_skipped` + `{reason: "no_input"}`
- `post_report_reflection_node_unhandled` + `{reason: errorClassName}`(对齐 Python `post_report_graph.py` line 92)

**注意 `coach_skipped: false` 不在 reflectionNode 输出中** — 该 channel 只由 coachNode 写。同样 `coach_error` 也只由 coachNode 写。Reflection 失败只写 `reflection_error`,绝不污染 coach_* 字段。

### 5.3 Error isolation 跨节点不变量

| 场景 | coach_skipped | coach_error | reflection_error | 备注 |
|------|---------------|-------------|------------------|------|
| 两个都成功 | `false` | `null` | `null` | happy path |
| Coach soft-skip(no_input)| `true` | `null` | `null` 或 error | reflection 独立 |
| Reflection soft-skip(no_input)| `false` 或 `true` | `null` 或 error | `null` | coach 独立 |
| Coach LLM error,Reflection 成功 | `false` | `"LLMError"` 或类似 | `null` | **error isolation 关键测例**(§11.5) |
| Coach 成功,Reflection LLM error | `false` | `null` | `"LLMError"` 或类似 | 反向对称测例 |
| 两个都 LLM error | `false` | error string | error string | graph 仍 resolve 完整 state(永不抛) |

**Invariant**:`(graph.invoke 永不抛错)`AND`(两条分支无论何状态 都到 END)`。这是 dev.d 的 §11.4 / §11.5 测试核心断言。

## 6. 并行 fan-out 边拓扑

### 6.1 拓扑图(对齐 Python `post_report_graph.py` line 8 / line 98-106)

```
START ──┬──► coach_node ──────┐
        │                     ├──► END
        └──► reflection_node ─┘
```

节点名集合 `{ "coach_node", "reflection_node" }`(L0 锁第二次出现)。

**关键观察**:与 turn_graph 不同 — 本图**没有 fan-in 同步节点**。两条分支独立到 END。LangGraph.js 0.2.74 Pregel runtime 对此形态的处理:每个 super-step 会调度所有 outgoing-from-START 的节点并行,END 是 implicit barrier(graph.invoke 等所有写入 END 的分支完成后才 resolve)。

### 6.2 4 边定义

```ts
graph
  .addNode("coach_node",      (s) => coachNode(s, deps))
  .addNode("reflection_node", (s) => reflectionNode(s, deps))
  .addEdge(START, "coach_node")
  .addEdge(START, "reflection_node")
  .addEdge("coach_node", END)
  .addEdge("reflection_node", END)
  .compile();
```

4 条边,顺序与 Python `post_report_graph.py` line 103-106 完全一致。

### 6.3 与 turn_graph / intake_graph 形态对比

| 图 | 形态 | fan-in 节点? | 边数 | 备注 |
|----|------|--------------|------|------|

| intake_graph (M3.3.2) | sequential | 不适用 | 4 | parse → research → predict |
| post_report_graph (M3.3.3) | **fan-out 无 fan-in** | **否** | **4** | START 分两路独立到 END |

dev.d 在 PR description 中显式声明:**"START 同时连到两个 node,两个 node 同时连到 END,中间无 fan-in 同步节点"**,以阻止 reviewer 误加 "merge node" / 误把第二条 edge 改成 sequence。

### 7.4 `applyReportSanitization` — 4-step pipeline

`sanitizers.ts` 中的核心 helper,对 raw LLM output 依次应用:

#### Step 1: `coercePassLikelihood(raw, overall_score, _matchScore?)`: PassLikelihood

逐字翻译 Python `apps/api/app/domain/reports/service.py` line 95-136。

- 若 `raw ∈ {"中上", "中", "中下"}`(即 `PassLikelihoodSchema` 通过)→ 直接返回 raw
- 否则查 `overall_score`:
  - `>= 80` → `"中上"`
  - `>= 65` → `"中"`
  - 否则 → `"中下"`
- WARN log key:`pass_likelihood_illegal_value` + `{raw, derived, overall_score}`(对齐 Python line 129-134)

**额外建议映射表**(dev.a 在 helper 内部首先做字面量映射,再 fall back 到 score-based)— 提高用户体验、减少 80 分阈值踩边导致频繁降档:

| LLM raw output(字面量) | 强制映射 |
|--------------------------|----------|
| `"中上"` / `"高于中等"` / `"应该会过"` / `"倾向通过"` / `"较高概率通过"` | `"中上"` |
| `"中"` / `"持平"` / `"中等"` / `"不确定"` / `"五五开"` | `"中"` |
| `"中下"` / `"低于中等"` / `"倾向不通过"` / `"应该不会过"` / `"较低概率通过"` | `"中下"` |
| 其他(含 `"不建议"` / `"不通过"` / `null` / `""` 等)| `coercePassLikelihood` 走 score-based fallback |

**Judgment call**:Python `coerce_pass_likelihood` 只走 score-based fallback,不做字面量映射 — 这是 v3.1 行为。**dev.a 把字面量映射作为新增功能引入**(本 doc §13 risk #2 备案),理由:macOS 无 service 层兜底,UI 直接消费 agent 输出,字面量层次更稳。Python 后续可补回(不在本 loop 范围)。

#### Step 2: `normalizeDimensions(dims): DimensionScore[]`

逐字翻译 Python `apps/api/app/domain/reports/service.py` line 151-182。

- 输入:LLM 输出的 `dimensions` 数组(可能 0 / 3 / 5 项,name 已通过 `DimensionScoreSchema` 验过都是 `DimensionNameSchema` 5 个之一)

- WARN log key:`dimension_missing_padded` + `{name}`(每 missing dim 一次)

**Edge case**:如 LLM 输出 `dimensions=[]`(v3.1 legacy),`normalizeDimensions` 返回 5 项 placeholder。这是 service 层调整,不在 schema 锁内 —— `ReportAgentOutputSchema.dimensions: z.array(...).default([])` 仍接受空数组(不改 schema)。

#### Step 4: `aiVerdictRegexScan(ai_verdict): string`

**ai_verdict 后置 regex 扫**(超出 12 禁止词清单的恶劣词捕捉):

```ts
const AI_VERDICT_BANNED_REGEX = /(差|失败|不及格|不行|不通过|垃圾|废物|拉胯|烂)/;

export function aiVerdictRegexScan(text: string | null | undefined): string | null {
  if (text == null || text === "") return text ?? null;
  if (AI_VERDICT_BANNED_REGEX.test(text)) {
    return "请教练查看维度评分综合评估";  // Same as Step 3 ai_verdict fallback
  }
  return text;
}
```

**注意**:这一步在 Step 3 之后。Step 3 已用 12 禁止词清单扫,但清单是封闭集(12 词),regex 用于补充 catch 字符级模式(如 `"差距很大"`已在 12 词清单中,但 `"差到没法看"` 不在 → regex `差` 可捕)。

**风险**:regex 过宽可能误伤(如 `"差不多达标"` 也含 `差` → 误替换)。dev.a 测试中包含正样本 + 负样本 + 边缘样本各 5+ 条:
- 正:`"表现很差"` / `"完全失败"` / `"不及格"` → 应被替换
- 负:`"差异化优势"` / `"业务直觉很好"` / `"建议加强"` → 应原样通过
- 边缘:`"差不多达标"` → 当前 regex 会替换;dev.a 可考虑用 `\b` 词界或负向先行(`(?!异化|不多)差`)精炼

dev.a 在 `__tests__/reportAgent.test.ts` 中对每条样本断言。若误伤率高,扩 regex 黑名单字典而非贪心匹配。

### 7.5 12 禁止词 fuzz N=100 测试

**文件路径**:`apps/desktop/src/core/agents/report/__tests__/reportAgent.test.ts`

**LCG 参数**(对齐 M3.3.2 research-privacy.fuzz):
- seed = 42
- multiplier = 1664525
- increment = 1013904223
- modulus = 2^32

**fuzz 形态**:每次迭代随机生成一个 LLM "raw output",在 `summary` / `next_actions` / `ai_verdict` 之一随机注入 12 禁止词中的一个。断言 `applyReportSanitization(raw)` 后该字段被 fallback 替换。

```ts
it("★ FUZZ N=100 ★ — applyReportSanitization replaces ALL 12 forbidden words across all sanitized fields", async () => {
  const rng = makeLcg(42);
  let leakCount = 0;

  for (let i = 0; i < 100; i++) {
    const word = FORBIDDEN_TONE_WORDS[Math.floor(rng() * FORBIDDEN_TONE_WORDS.length)];
    const fieldChoice = Math.floor(rng() * 3);  // summary | next_actions[0] | ai_verdict

    const raw: ReportAgentOutput = makeMinimalValidOutput();
    if (fieldChoice === 0) raw.summary = `候选人${word},需要重新考虑`;
    else if (fieldChoice === 1) raw.next_actions = [`${word},建议放弃`];
    else raw.ai_verdict = `综合评价:${word}`;

    const sanitized = applyReportSanitization(raw);

    const stillContainsForbidden =
      scanForbiddenTone(sanitized.summary).length > 0 ||
      sanitized.next_actions.some((a) => scanForbiddenTone(a).length > 0) ||
      (sanitized.ai_verdict !== null && scanForbiddenTone(sanitized.ai_verdict).length > 0);

    if (stillContainsForbidden) leakCount++;
  }

  expect(leakCount).toBe(0);
});
```

**关键断言**:`leakCount === 0` — 100 次全部被 fallback 替换。

```ts
  text: string,
  ai_verdict: string | null,
```

```ts
  const seen = new Set<string>();
  const out: string[] = [];
  for (const item of items) {
    const s = item.trim();
    if (!s || seen.has(s)) continue;
    seen.add(s);
    out.push(s);
  }
  return out;
```

## 12. PostReportGraphDeps + buildPostReportGraph 工厂

```ts
import { StateGraph, START, END } from "@langchain/langgraph";
import type { StateGraphArgs } from "@langchain/langgraph";

export interface PostReportGraphDeps {
  llm: LLMProvider;
  logger?: {
    info?(msg: string, meta?: Record<string, unknown>): void;
    warn?(msg: string, meta?: Record<string, unknown>): void;
  };
}

export function buildPostReportGraph(deps: PostReportGraphDeps) {
  const graph = new StateGraph<PostReportState>({ channels })
    .addNode("coach_node",      (s) => coachNode(s, deps))
    .addNode("reflection_node", (s) => reflectionNode(s, deps))
    .addEdge(START, "coach_node")
    .addEdge(START, "reflection_node")
    .addEdge("coach_node", END)
    .addEdge("reflection_node", END);
  return graph.compile();
}
```

返回类型由 LangGraph.js 推断(不显式标 `CompiledStateGraph<PostReportState>`,与 turn_graph / intake_graph `build*Graph` 一致)。
