## 2. L0 红线总结(必读)

本设计严格对齐 `AGENTS.md` L0 红线与 PRD §4.4。任何与下列任一条冲突的实现 = 节点 fail。

### 2.1 §C3 — API Key 不出 Swift 边界(critical)

**`keychain.get(account)` 的返回值绝不允许包含 secret 字面量**。

- ❌ 严禁:`{ exists: true, secret: "sk-..." }`
- ✅ 唯一允许:`{ exists: bool }`(secret 不存在时也可返回 `null`,但项目惯例选 `{ exists: bool }` 以便统一类型)

Secret 由 Swift 内部 `LLMGateway` / `ASRGateway` 在 stack 内消费(`KeychainService.read(...) -> URLRequest.setValue("Authorization", ...)`),**永远不出 Swift → JS 这条边界**。这条规则是 §C3 与反模式 §K #6 的合并锁,直接锁死 Bridge 协议形态。

### 2.2 §K #6 反模式显式拒绝

> "为了减少 Bridge 调用次数,把 API Key 通过 messageHandler 传给 JS 层临时存内存"

**本设计明确拒绝该反模式**。理由:
1. JS 内存对 sandbox 外的 attacker 视作可读(WebKit JIT、devtools、远程 XSS via 第三方依赖供应链);Keychain `kSecAttrAccessibleAfterFirstUnlock` 提供的 OS 级保护一旦"过桥"立即失效。
2. Bridge 调用次数不是瓶颈:LLM/ASR 的 secret 消费发生在 Swift gateway 内部,JS 全程不接触;每次请求 0 次跨 Bridge secret 传递。
3. App Store review 历史记录:任何把 API key 持久化到 WebView storage / `localStorage` / IndexedDB 的设计有被拒先例(Guideline 5.1.1, 5.1.2)。

### 2.3 §A0 / §A0.1 / §A0.2 — Sandbox 与 entitlements

- Bridge 注册是 in-process(WebKit `WKUserContentController`),**不需要新增任何 entitlement**。这是 v3.4 vs Tauri/方案 A 的关键优势:`com.apple.security.network.server` / `com.apple.security.cs.disable-library-validation` 等禁项在本设计中**不出现**。
- 永久排除清单(本设计不引入):Tauri / Python sidecar / faster-whisper / PyAV / 任何 `network.server` 监听。

### 2.4 §B9 — Bridge 协议双端契约

任何 method 增删 / 改签名 = 同 commit 内必须同时修改:
1. Swift Codable struct(`apps/macos/Eatit/Bridge/...`)
2. JS Zod schema(`apps/desktop/src/services/nativeBridge/...`)
3. Vitest 单测(happy + ≥1 error)
4. Swift XCTest(同上)
4 项缺一不可。详见 §9 双端契约校验机制。

### 2.5 §F — Test Floor

每个 method 必须有 happy path + ≥1 error case 双端测试。错误码字符串需 hard-code 不依赖 enum-to-string,以防 typo 漂移。

## 3. 通道形态(Channel Shape)

### JS → Swift

```js
const reply = await window.webkit.messageHandlers.eatit.postMessage(payload);
```

- 注册名锁:**`eatit`**(锁;不得改名,任何 PR 改名 = block)。
- 用 `WKScriptMessageHandlerWithReply`(macOS 14+ 提供,本项目最低部署 14)启用 reply handler 模式,直接对应 `BridgeRequest → BridgeResponse` 一问一答语义,JS 侧 `postMessage` 自动返回 `Promise<BridgeResponse>`。

### Swift → JS(异步事件 / 流式)

```swift
let payload = try BridgeEvent.encodeJSON(...)
webView.evaluateJavaScript("window.eatitBridge.dispatch(\(payload))")
```

- 异步流式事件不能走 reply 通道(reply 是一次性的);走 `evaluateJavaScript` 调 JS 注册的全局 dispatcher `window.eatitBridge.dispatch`。
- `window.eatitBridge` 全局命名空间锁:JS 启动期由 `nativeBridge.ts` 初始化挂载,任何 method 改动同步更新 dispatcher 的 event handler 表。

## 4. 消息 Schema(JSON / Zod / Codable)

三类消息形态:`BridgeRequest`、`BridgeResponse`、`BridgeEvent`。**JSON shape 是权威**,Zod / Codable 是双端镜像。

### 4.1 BridgeRequest

JSON shape:

```json
{ "id": "uuid-v4", "method": "namespace.action", "params": { ... } }
```

- `id`: UUID v4,JS 生成,用于 response 匹配。即使 Apple `WithReply` 模式自动配对,id 仍保留,便于日志关联与错误诊断。
- `method`: `<service>.<action>` 格式,小写 + `-` 连字符或 camelCase action(本表全部 camelCase action,如 `keychain.save`、`db.query`、`llm.chatStream`)。
- `params`: method-specific(见 §5),JS 端用 Zod schema 校验,Swift 端用 method-specific Codable struct 反序列化。

Zod 占位(在 `nativeBridge/schemas/request.ts`):

```ts
export const BridgeRequestSchema = z.object({
  id: z.string().uuid(),
  method: z.string().regex(/^[a-z]+\.[a-zA-Z]+$/),
  params: z.unknown(),
});
```

Codable 占位(在 `apps/macos/Eatit/Bridge/BridgeMessage.swift`):

```swift
struct BridgeRequest: Codable {
    let id: String
    let method: String
    let params: AnyCodable    // 由 router 二次解码到具体 ParamsType
}
```

### 4.2 BridgeResponse(discriminated union on `ok`)

成功 shape:

```json
{ "id": "uuid-v4", "ok": true, "data": { ... } }
```

失败 shape:

```json
{ "id": "uuid-v4", "ok": false, "error": { "code": "service.error-kind", "message": "developer-readable english" } }
```

强调:**discriminated union**(以 `ok` 字段区分),Zod 与 Codable 都按此建模,避免 optional 字段歧义。

Zod 占位:

```ts
export const BridgeResponseSchema = z.discriminatedUnion("ok", [
  z.object({ id: z.string().uuid(), ok: z.literal(true), data: z.unknown() }),
  z.object({ id: z.string().uuid(), ok: z.literal(false),
    error: z.object({ code: z.string(), message: z.string() }) }),
]);
```

Codable 占位:

```swift
enum BridgeResponse: Codable {
    case success(id: String, data: AnyCodable)
    case failure(id: String, error: BridgeError)
    // init(from:) / encode(to:) 按 ok 字段 dispatch
}

struct BridgeError: Codable { let code: String; let message: String }
```

### 4.3 BridgeEvent

```json
{ "type": "stream-chunk" | "asr-partial" | "asr-final" | "asr-end",
  "streamId": "uuid-v4", "payload": { ... } }
```

- 不带 `id`(因为不是请求-响应配对,而是 fire-and-forget push)。
- `streamId` 由 originating Request 的 params 注入(JS 生成,Swift 回引);多个 event 共享同一 streamId 表示属于同一逻辑流。
- `type` 是固定枚举,新增 type 等同新增 method,触发 §B9 双端契约流程。

### 4.4 手写而非 codegen(决策)

**本版选手写双端 schema**,理由:

1. method 总量 18,人脑可一眼看完;codegen 工具链(如 typeshare / quicktype)的引入成本(配置 + CI 集成 + 调试)> 直接维护两份 schema 的成本。
2. 各 service params 类型差异大(SQL bytes / PCM ms 时间戳 / 文件 base64 / LLM messages 数组等),codegen 通用模板很难表达所有 case 的精细约束(例 `db.query.params` 需限制 SQL placeholder count = `params.length`),手写更精准。
3. 真正的安全网是 §9 的"同 commit 同改"discipline + Vitest/XCTest round-trip 测试,不是 codegen。

**何时重新评估** codegen:method ≥ 30 时(M3 新增 ≥12 个 method 或 plugin 系统接入)。

## 6. 错误码命名约定

### 6.1 模板与铁律

模板:**`<service>.<error-kind>`**,全小写 + 连字符 kebab-case 表述 error-kind。

- service 段 ∈ `{ keychain, db, file, pdf, audio, llm, asr, bridge }`(锁;新增需 PR 评审)。
- error-kind 段:动词或形容词短语,描述失败原因,**不**重复 service 名(如 `keychain.keychain-not-found` 是反例)。
- 错误码字符串在双端 **完全 hard-code**,不依赖 enum-to-string serialization,以防 typo / case 漂移。
- `code` 是机器读 + 开发者读;`message` 是开发者读英文短语(给日志看);**用户文案由 JS 上层根据 `code` 查 i18n 表决定**,Bridge 层不本地化。

### 6.2 Starter Codebook(M2.1.dev 以此初始化常量表)

| service | code | 触发条件 |
|---|---|---|
| keychain | `keychain.not-found` | 指定 account 不存在 |
| keychain | `keychain.duplicate` | save 时 account 已存在(若选择 update 策略则不报) |
| keychain | `keychain.access-denied` | OS 拒绝(用户在 Keychain.app 改了 ACL 等) |
| db | `db.constraint-violation` | UNIQUE / FK / NOT NULL 违反 |
| db | `db.locked` | SQLite_BUSY / database is locked |
| db | `db.serialization-failure` | tx 重试耗尽 |
| file | `file.user-cancelled` | NSOpenPanel 用户点 Cancel |
| file | `file.size-exceeded` | 单文件超过 PRD 限额(M2.4 锁数值) |
| file | `file.unsupported-format` | accept 列表不包含该 UTI |
| pdf | `pdf.parse-failed` | PDFKit 返回 nil document |
| pdf | `pdf.encrypted` | PDF 受密码保护 |
| audio | `audio.permission-denied` | macOS Microphone privacy 拒绝 |
| audio | `audio.device-unavailable` | 无可用输入设备 / 设备被占用 |
| llm | `llm.rate-limited` | provider 429 |
| llm | `llm.context-too-long` | provider 4xx 上下文溢出 |
| llm | `llm.tool-call-malformed` | tool_calls JSON 解析失败 |
| asr | `asr.connection-failed` | WS 握手失败 |
| asr | `asr.auth-failed` | provider 鉴权 401/403 |
| asr | `asr.protocol-error` | WS 帧格式不符预期 |
| bridge | `bridge.method-not-found` | router 收到未注册 method |
| bridge | `bridge.params-invalid` | Codable 反序列化失败 / 必填字段缺失 |
| bridge | `bridge.internal-error` | router 内部异常(catch-all,需配 message 详情) |

### 6.3 错误码使用 contract

- `code` 必填,`message` 必填(可短至 `"unknown"`,但不得为 null/empty string)。
- 不得透传 OSStatus 数值或 SQLite errcode 到 message;用上表枚举包装。
- 单元测试必须断言确切 code 字符串(不要 `expect(...).toMatch(/keychain/)`,要 `expect(code).toBe("keychain.not-found")`)。

## 7. 流式协议

适用 method:`llm.chatStream`(主),`audio.start` / `asr.start`(事件推 transcript)。

### 7.1 完整流程(以 `llm.chatStream` 为例)

1. **JS 创建 streamId 并发起 Request**:

   ```js
   const streamId = crypto.randomUUID();
   const reply = await bridge.call("llm.chatStream",
     { messages, model, streamId });
   // reply.data === { streamId, started: true }
   ```

   streamId 由 JS 生成(避免 Swift 异步分配带来的额外 round-trip);Swift 也允许在 params 缺失时回退生成,但本版规定 **JS 必须传**,缺失返回 `bridge.params-invalid`。

2. **Swift 立即返回 BridgeResponse** `{ id, ok: true, data: { streamId, started: true } }`。
   Promise 在 JS 端 resolve,不阻塞后续 chunk。

3. **Swift 异步推 BridgeEvent**(0..N 次):

   ```json
   { "type": "stream-chunk", "streamId": "...",
     "payload": { "delta": "Hello", "done": false } }
   ```

4. **结束 chunk**(单一终止条件,done=true):

   ```json
   { "type": "stream-chunk", "streamId": "...",
     "payload": { "delta": "", "done": true, "finishReason": "stop" } }
   ```

   `finishReason` ∈ `{ "stop", "length", "tool_calls", "content_filter", "error" }`(对齐 OpenAI 兼容 API)。
   `error` 时同时 payload 含 `error: { code, message }`(同 BridgeError shape)。

5. **JS 端 AsyncIterator wrapper**(M2.1.dev 内联实现,~10 行):

   ```ts
   async function* llmChatStream(req: LLMChatParams): AsyncIterable<string> {
     const streamId = crypto.randomUUID();
     const queue = bridge.openStream(streamId);   // 注册到 dispatcher
     await bridge.call("llm.chatStream", { ...req, streamId });
     for await (const evt of queue) {
       if (evt.payload.done) return;
       yield evt.payload.delta;
     }
   }
   ```

   `bridge.openStream` 由 `nativeBridge.ts` 提供,内部维持 `Map<streamId, AsyncQueue>`,`window.eatitBridge.dispatch` 命中后入队。

### 7.2 取消(本版策略)

不引入通用 `bridge.cancelStream(streamId)`。每个 streaming method 自带 stop:`asr.stop` / `audio.stop`;`llm.chatStream` 由 JS `AbortController.signal` 在 fetch 级别取消(M2.6.dev 实现,本 doc 不展开)。

未来 method ≥30 时再评估通用 cancel(见 §12)。

## 8. WebView messageHandler 注册

### 8.1 Swift 侧注册

在 `WebViewController.viewDidLoad()`(或 `loadView()`)内:

```swift
let config = WKWebViewConfiguration()
let router = BridgeRouter()
config.userContentController.addScriptMessageHandler(
    router, contentWorld: .page, name: "eatit"
)
// macOS 14+ 用 WKScriptMessageHandlerWithReply 协议,自动支持 reply handler
```

- 注册名:**`eatit`**(锁;PRD §4.4.1 已锁)。
- `BridgeRouter` 实现 `WKScriptMessageHandlerWithReply.userContentController(_:didReceive:replyHandler:)`,在 handler 内解码 BridgeRequest → 路由到 method handler → 编码 BridgeResponse → 调用 `replyHandler`。
- `contentWorld: .page` (非 isolated),让 `window.eatitBridge` 也能在主世界注册。

### 8.2 JS 侧 boilerplate

在 `nativeBridge.ts` 启动期(`main.tsx` import-side-effect 即可):

```ts
declare global { interface Window {
  webkit?: { messageHandlers: { eatit: { postMessage(msg: unknown): Promise<BridgeResponse> } } };
  eatitBridge: { dispatch(evt: BridgeEvent): void };
} }

window.eatitBridge = { dispatch(evt) { /* fan-out to streamId handlers */ } };

export async function call<T>(method: string, params: unknown): Promise<T> {
  const id = crypto.randomUUID();
  const req: BridgeRequest = { id, method, params };
  const reply = (await window.webkit!.messageHandlers.eatit.postMessage(req)) as BridgeResponse;
  if (!reply.ok) throw new BridgeException(reply.error);
  return reply.data as T;
}
```

`postMessage` 在 macOS 14+ + `WithReply` 模式下原生返回 `Promise`;无需手写 id-keyed correlator。

### 8.3 不需要新 entitlement

注册 messageHandler 是 in-process API(`WKUserContentController`),沙盒内合法,**不需要任何额外 entitlement**。这是 v3.4 vs Tauri 方案的根本简化:无 `network.server`,无 `disable-library-validation`,App Store review 面板平。

## 9. 双端契约校验机制(手写策略)

### 9.1 决策与文件布局

**Strategy: 手写 dual schema**(理由见 §4.4)。落地文件布局(M2.1.dev 创建,M2.2+ 增量):

- Swift:`apps/macos/Eatit/Bridge/BridgeMessage.swift`(三类消息基类型)+ `apps/macos/Eatit/Bridge/Methods/<MethodName>.swift`(每 method 一个 params/result Codable struct)
- TS:`apps/desktop/src/services/nativeBridge/messages.ts`(三类消息 Zod)+ `apps/desktop/src/services/nativeBridge/methods/<methodName>.ts`(每 method 一个 Zod schema 与 TS 类型)
- 集中导出:`apps/desktop/src/services/nativeBridge/index.ts` 暴露 `call(method, params)` + 类型化 wrapper(如 `bridge.keychain.get(account)`)

### 9.2 Method 增删 / 改 SOP(§B9 锁)

**任何 method 增删或签名修改,在同一 commit 内必须包含全部 4 项**:

1. Swift Codable struct(新增 `Methods/<MethodName>.swift` 或修改既有)
2. JS Zod schema(新增 `methods/<methodName>.ts` 或修改既有)
3. Vitest 单测:happy path + ≥1 error case(`apps/desktop/src/services/nativeBridge/__tests__/<methodName>.test.ts`)
4. Swift XCTest:happy path + ≥1 error case(`apps/macos/EatitTests/Bridge/<MethodName>Tests.swift`)

PR 检查脚本(M2.1.dev 实现 `scripts/check-bridge-sync.sh`):git diff 中若 `methods/*.ts` 改动 ≠ `Methods/*.swift` 改动,CI fail。

### 9.3 Cross-end Sanity Tests

M2.1.dev 内置三类双端 round-trip 测试(以 BridgeRequest 为骨架,后续 method 复用):

1. **JSON byte-equal round-trip**:Swift encode → JS Zod parse → JS stringify → Swift decode → 字段全等。
2. **camelCase 一致性 lint**:CI 脚本扫 method name 与 params field 命名违规。
3. **Error code lock 测试**:Swift 与 JS 各自维护一份 `BridgeErrorCodes` 常量表,测试断言两表 set-equal(防止单端漏改)。

### 9.4 命名风格统一

- method 名:`<service>.<action>`,action 用 camelCase(`chatStream`、`extractText`、`dropEnable`);service 全小写。
- 字段名:JSON 使用 camelCase(`streamId` 而非 `stream_id`,`rowsAffected` 而非 `rows_affected`);Swift 用 `CodingKeys` 不映射(同名),TS 原生即 camelCase。
- streamId 永远是 UUID v4 字符串,不用 number。

## 11. 测试矩阵(对应 §F Test Floor)

M2.1.dev 必须落盘的测试(后续 method 增量补,M2.1 仅骨架):

1. **schema round-trip**:BridgeRequest / BridgeResponse / BridgeEvent 各 1 条 happy + 1 条 invalid JSON → Zod reject + Codable throw。
2. **method routing**:`bridge.method-not-found` 路径(Swift router 收到未注册 method 返回正确 error code)。
3. **params 校验**:任意 method(可选 `keychain.save`)缺字段 → `bridge.params-invalid`。
4. **error code 字符串锁**:断言 starter codebook 全集双端一致。
5. **streamId discipline**:`llm.chatStream` 缺 streamId → `bridge.params-invalid`(spec 锁定 JS 必须传)。

每个 M2.2+ service 节点新增 method 时,补 method-specific happy + error,测试矩阵自然增长。

## 12. 已知未决 / Future Work

仅记录,不在本节点 / M2.1.dev 范畴。

- **Codegen 自动化**:method ≥30 时(M3 plugin 系统或多 LLM provider 接入触发),评估 typeshare / quicktype 引入。当前 18 个 method 不值得。
- **Bridge 性能(JSON serialize cost)**:LLM 大消息历史 + base64 文件可能让单次 postMessage payload >1MB。WebKit `WithReply` 在 ARM64 实测可承受;M2.6.dev 与 M2.4.dev 落地后做 micro-bench,若 P50 >50ms 评估 chunked / shared memory(目前优先级低)。
- **多 stream 并发取消**:本版无统一 cancel,各 method 自带 stop。M3.4 UI 集成完成后若发现取消语义反复重写,引入 `bridge.cancelStream(streamId)`。
- **`file.dropEnable` 事件 shape**:本 doc 仅锁 method 表项,实际 drop event 形态由 M2.4.arch 决定(payload 字段命名 / 是否拆 multi-file 等)。届时同步更新本 doc §5 表第 8 行。
- **`PrivacyInfo.xcprivacy` 中 `audio.start` 隐私字符串**:M6.x 上架前补,本 doc 不锁。
- **JS 端 Bridge 抽象层是否暴露给 React Hook**:M3.4 决定 hook 形态(`useLLMStream` 等),本 doc 仅锁 underlying call API。
